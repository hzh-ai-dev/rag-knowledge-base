# 检索增强生成（RAG）技术白皮书

## 一、为什么需要 RAG

大语言模型存在三个固有问题：知识存在截止日期、无法访问企业内部私有数据、容易产生幻觉。
微调（Fine-tuning）可以注入知识，但成本高、更新慢，且难以溯源。

检索增强生成（Retrieval-Augmented Generation, RAG）的思路是：在生成之前先从外部知识库
检索相关内容，把检索结果作为上下文交给模型，让模型「看着资料回答」。这样做的好处是
知识可实时更新、来源可追溯、无需重新训练模型。

## 二、标准流程

一次完整的 RAG 请求分为四个阶段：

1. **索引（Indexing）**：文档解析 → 分块 → 向量化 → 写入向量数据库。离线完成。
2. **检索（Retrieval）**：将用户问题向量化，在向量库中做相似度搜索，召回 top-k 个文本块。
3. **增强（Augmentation）**：把召回的文本块按编号拼装进提示词模板，与问题一起构造消息。
4. **生成（Generation）**：大模型基于上下文生成答案，并标注引用编号。

## 三、关键设计决策

### 3.1 分块策略

分块大小是最重要的超参数之一。块太小会丢失上下文，块太大会引入噪声并稀释关键信息。
实践中 500 到 800 字符是较稳妥的区间，相邻块之间保留 10% 到 20% 的重叠，
可以缓解「答案恰好被切在边界」的问题。

对于中文文档，分隔符应优先选择段落换行与中文句末标点（。！？；），
而不是按英文空格切分，否则容易切断句子。

### 3.2 混合检索

纯向量检索擅长语义匹配，但对专有名词、产品型号、编号类查询表现不佳，
因为这类词的语义空间表示往往不够区分。BM25 基于词频统计，恰好弥补这一短板。

把两路结果融合常用 RRF 算法，公式为：

    score(d) = Σ 1 / (k + rank_i(d))

其中 k 为平滑常数，通常取 60。RRF 只依赖排名而非分数，因此无需归一化两路分数量纲，
鲁棒性好，实现也简单。

### 3.3 引用溯源

要求模型在答案中标注 [1][2] 这样的编号，并在提示词中明确「只能依据资料作答」，
可以显著降低幻觉率。同时前端展示来源文件与页码，让用户可以自行核验，提升可信度。

### 3.4 评估

没有评估就没有优化。常用的离线指标包括：

- **召回率 / Hit@k**：正确文档是否出现在 top-k 结果中。
- **MRR**：第一个正确结果排名的倒数均值，衡量排序质量。
- **忠实度（Faithfulness）**：答案是否完全由检索到的上下文支撑，需要 LLM 或人工判别。

建议在上线前构建 50 到 200 条问题的评测集，每次调整分块、检索参数后都跑一遍，
用数据驱动决策，而不是凭感觉。

## 四、常见失效模式

| 失效现象 | 可能原因 | 应对措施 |
| --- | --- | --- |
| 检索不到相关内容 | 分块粒度不当 / 缺少关键词检索 | 调整分块大小，开启混合检索 |
| 检索到了但对不上 | 问题与文档用词差异大 | 增加查询改写（Query Rewriting） |
| 答案与资料矛盾 | 上下文过长导致模型忽略 | 减少 top_k，引入重排 |
| 答非所问 | 提示词约束不足 | 明确「无答案时拒答」规则 |

## 五、进阶方向

- **查询改写**：用大模型先把用户口语化问题改写成更适合检索的形式。
- **重排（Rerank）**：用交叉编码器（如 bge-reranker）对召回结果精排，通常能提升 5% 到 15% 的准确率。
- **父文档检索**：用小块做检索，命中后返回其所属的大块作为上下文，兼顾精度与完整性。
- **多跳检索**：复杂问题拆成多个子问题分别检索，再汇总回答。
